CryNet

Flashing every unit, offline — the complete step-by-step guide

This document is written so you can put the current firmware on the hub, both cot nodes and the wearable — or on brand-new boards — by yourself, at home, with no compiler, no IDE, no internet and nobody to ask. One command per unit. Everything the commands print, what it should look like when it worked, and what to do when it did not, is in here.

The five rules, before anything else

  1. A COM port number is not an identity. Windows renumbers ports when you replug. The MAC address burned into the chip is the identity. Check §3 every session.
  2. Flash the hub first. A new hub reads both old and new node telemetry; an old hub misreads the new nodes. Hub, then nodes, then wearable — never another order.
  3. Run --check before the first flash of the day. A HASH MISMATCH means the image is damaged — stop.
  4. The flash never writes NVS. A node keeps its id; the hub keeps its network and token settings. You set those once, and reflashing never erases them.
  5. Back up before you flash (§4). Two minutes per board, and it is the only way back.

0 — One-time setup: the one tool and the folder

The whole offline path needs exactly one program: esptool, which writes firmware to a board over USB. It compiles nothing, so it needs no Arduino core, no PlatformIO, no compiler and no network. On this machine it is already installed:

%USERPROFILE%\.platformio\packages\tool-esptool\esptool.exe

The helper scripts are Python and additionally want pyserial (pip install pyserial). Both are one-time installs. On a brand-new machine, copy tool-esptool\ across on a USB stick, or pip install esptool once while you do have internet — after that, everything below works fully offline.

The firmware images live in the repository, already built:

firmware/prebuilt/
├── SHA256SUMS         the hash of every image — proof it is intact
├── BUILD_INFO.json    which source each image was built from
├── hub/               bootloader.bin  partitions.bin  firmware.bin
├── node/              bootloader.bin  partitions.bin  boot_app0.bin  app.bin
└── wearable/          bootloader.bin  partitions.bin  boot_app0.bin  app.bin

No network? Copy the whole fp-two-node folder onto a USB stick and work from the copy. Everything in this guide runs from it unchanged.

2 — Step 2: learn which board is on which port

Do this every session, before the first flash. Windows assigns COM numbers from the socket and the plug order, so the same board gets a different number when you move it. The port is never guessed: a flash aimed at the wrong port once parked a node in its bootloader (incident I-40), which is why the scripts make you name it.

2a. List what is plugged in

python firmware/tools/flash_unit.py --list

Read it like this:

What Windows showsWhat it is
USB-Enhanced-SERIAL CH343 (COMxx)the hub — it has a CH343 USB-serial bridge
USB Serial Device (COMxx)an ESP32-C3 on its own native USB — a cot node or the wearable; you cannot tell them apart from this line alone

2b. Ask each board who it is

python firmware/tools/who_is_who.py COM30 COM31 COM32 COM37

This resets each board, reads its boot banner, and flashes nothing. A cot node answers with its id and its MAC:

CryNet node firmware — Stage 2b
node id 2 (saved; the MAC would have said 7)
node 2  mac 90:DA:72:87:CB:98

The wearable answers with its OLED and Bluetooth lines:

[oled] up
[ble] hub connected
[ble] state: 2 cot(s), mask 0x00

Treat this as a memory aid, not as an answer. Verify with 2a and 2b every time.

2d. A board that has never been flashed

A new board prints no CryNet banner, so read its MAC straight from the chip:

& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32c3 --port COM31 chip-id

That prints the MAC and proves the board answers on that port at all. Write it next to the board.

3 — Step 3: back the board up first

Before every flash. Two minutes, and it is the only way back.

python firmware/tools/flash_unit.py --role node --port COM31 --backup

--backup reads the board's entire flash to a file in %TEMP%, then proceeds only when you run the flash command again. By hand, the same thing:

# a cot node or the wearable (ESP32-C3, 4 MB flash)
& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" `
    --chip esp32c3 --port COM31 read-flash 0x0 0x400000 "$env:TEMP\fullflash_31.bin"

# the hub (ESP32-S3, 16 MB flash) — bigger, so it takes longer
& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" `
    --chip esp32s3 --port COM32 read-flash 0x0 0x1000000 "$env:TEMP\fullflash_hub_32.bin"
Copy the backup out of %TEMP% into a folder you keep (keep it named for the board and the date — node1_2026-11-25.bin). Windows clears %TEMP% on its own schedule, and a backup that disappears with it was never a backup. Rollback is one command; see §8.

4 — Step 4: flash — hub first, then the nodes, then the wearable

The order is not a preference. The current node sends a 32-byte telemetry frame; the pre-D-83 node sent 34 bytes with a battery field in the middle. The current hub reads both, so a not-yet-reflashed node cannot confuse it — but an old hub can only read the old 34 bytes. Flash the hub first, and a node never meets a hub that misreads it.

One command per unit, with its own port named — the port you verified in §2:

the hub, always first:
python firmware/tools/flash_unit.py --role hub     --port COM32 --log 25

cot node 1:
python firmware/tools/flash_unit.py --role node    --port COM31 --log 15

cot node 2:
python firmware/tools/flash_unit.py --role node    --port COM37 --log 15

the wearable:
python firmware/tools/flash_unit.py --role wearable --port COM30 --log 15

--log N reads the board's boot log for N seconds after the flash, which is how you see the §5 lines without opening a second tool. Drop it if you do not want it.

What the tool actually does, and what it deliberately does not

  • Each command writes the images region by region, exactly where the partition table says: bootloader to 0x0, partition table to 0x8000, application to 0x10000 (and boot_app0.bin to 0xe000 on the C3 boards).
  • NVS is never written — it sits at 0x9000–0xE000 on the nodes and 0x9000–0xF000 on the hub, and no command touches it. So a node keeps its id and the hub keeps its network settings across every reflash.
  • The hub is written as three images, not one combined file. A combined image must be written in DIO mode; the ROM on this board cannot read the flash in QIO before the bootloader has set up its own timing, and a QIO image makes the chip watchdog-reset in a loop. The three-image write is the safe one, and the shipped hub images are already DIO.

The same thing by hand (no Python needed)

# the hub
& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" `
    --chip esp32s3 --port COM32 --baud 921600 write-flash `
    0x0     firmware\prebuilt\hub\bootloader.bin `
    0x8000  firmware\prebuilt\hub\partitions.bin `
    0x10000 firmware\prebuilt\hub\firmware.bin

# a cot node or the wearable — same command, different folder: node\ or wearable\
& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" `
    --chip esp32c3 --port COM31 --baud 921600 write-flash `
    0x0     firmware\prebuilt\node\bootloader.bin `
    0x8000  firmware\prebuilt\node\partitions.bin `
    0xe000  firmware\prebuilt\node\boot_app0.bin `
    0x10000 firmware\prebuilt\node\app.bin

5 — Step 5: read the boot log — what good looks like

The hub

A good hub boot says, in this order (real lines from the current build):

I (864)  app_init: App version:      3acaf99          ← the commit it was built from
I (976)  crynet: CryNet hub — inference core (Stage 2a)
I (3502) crynet: RESULT: PASS — 4 probes, front end and model agree with the host
I (4259) ili9341: the panel is up: 320 x 240, rotation 2 (madctl 0x80)
I (3817) crylog: storage mounted: 4267 of 5775761 bytes used
I (3837) crylog: boot 104: 104 records kept, 1 still to send, next number 105
I (4074) crynet: hub-f9172f80 ready: network "Amazyn", dashboard https://…/api/v1/events
I (4368) link: node 1 is online
I (4368) link: node 2 is online

Three things carry the whole verdict:

  • RESULT: PASS — 4 probes — the hub's self-check agrees with the host about the model's arithmetic. If it says FAIL, stop and read the lines above it.
  • The App version line names a commit. The banner is the identity check (D-106): if the version it prints is older than the images you just wrote, something flashed the wrong file.
  • node 1 is online / node 2 is online, and the link: lines carry no bat field — its absence is how you know this build is running.

crylog: and crynet: lines say the record and the network stage came up. If instead you see “the cry log could not be opened”, the hub carries on and still buzzes the wrist — it just keeps no record. If you see “dashboard (not set -- log only)”, the record works; only the uploading is not configured yet (§7).

A cot node

node id 2 (saved; the MAC would have said 7)
node 2  mac 90:DA:72:87:CB:98
rms 0.0120  floor 0.0028  level 0.0083

node id n (saved) means the id you set is in NVS and survived the reflash — that is exactly right. node id n (derived from the MAC) on a board you have already named is a sign you are talking to a different board. With no microphone attached, rms 0.0000 is correct, not a fault: there is nothing on the data line to be anything but zero.

The wearable

[oled] up                       ← or: [oled] SSD1306 not found at 0x3C — check SDA 5 / SCL 6
[ble] hub found (30:30:F9:17:2F:80)
[ble] hub connected
[ble] state: 2 cot(s), mask 0x00

2 cot(s) is the hub telling it how many cots it hears; mask 0x00 means no cot is crying right now. The OLED line without a display attached still means the wearable works — the screen is optional to its job; the buzz is not.

6 — Step 6: a brand-new node needs its id set

A new node has no id in NVS, so it derives one from its MAC — the last byte, masked and plus one, so anything from 1 to 16. The hub watches cots 1 and 2 only, and two identical boards can derive the same number. Set the ids by hand; do not trust the derived value.

Open the node's serial console at 115200 baud (the same port as the flash; any serial terminal works) and type:

id 1        ← the first cot
id 2        ← the second cot

Each answers with the id saved into NVS. It survives every future reflash. The wearable and the hub need nothing like this: the wearable finds the hub by Bluetooth; the hub comes up, self-checks and starts listening.

7 — Step 7: the hub's record and the dashboard, set once

After a hub flash, three things to know. All of them are stored in NVS: type them once, never again — reflashing never erases them.

7a. Prove the record keeps every cry

Type logtest on the hub's serial console:

logtest: PASS -- a cry that finishes out of order is still sent

It runs the out-of-order-cry scenario against the real log component, on its own scratch file; your real records are not touched. If it ever says FAIL, do not trust the dashboard's record until it is looked at.

7b. The one router setting that is not optional

Set the router's 2.4 GHz channel to 6. The cots talk to the hub on channel 6 and the hub has one radio; on any other channel it deliberately drops the Wi-Fi so the cots stay audible. A hub on the wrong channel looks like "no network" forever, no matter what you type.

7c. Tell the hub where the dashboard is

net ssid Amazyn me_mine_me                          ← which Wi-Fi to join (once)
net set http://192.168.1.50:8787/api/v1/events      ← where records go (once)
net token <the-token>                               ← only for the hosted dashboard (once)
upload                                              ← send what is waiting, now
net                                                 ← check: batches, failures, last error

The hosted copy needs the router's channel 6 too, and its address is https://amazings-crynet.amazingadelowo.workers.dev/api/v1/events. The offline copy needs only python dashboard/server.py on any machine on the same network — it prints the exact net set line to type.

Verify the monitor does not need any of this: turn the router off, raise a test alert with alert 1 on the hub's console, and confirm the wrist still buzzes. Then log should show the record waiting. The system detects, alerts and records with no network at all; the dashboard empties it when one appears.

8 — Step 8: when something goes wrong

The board sits there and prints nothing — it is in the bootloader

The most common failure. A flash that stops partway — wrong chip, wrong port, a yanked cable — leaves the board in its bootloader, not running firmware. It looks dead. Bring it back:

& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32c3 --port COM31 run   ← node / wearable
& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32s3 --port COM32 run   ← hub

could not open port 'COMxx'

The port does not exist — the board is unplugged, or Windows renumbered it. Go back to §2 and re-identify. Do not guess.

Failed to connect to ESP32: Timed out waiting for packet header

Either the board is in the bootloader (above), or the wrong board is on that port. Settle it:

& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32c3 --port COM31 chip-id

The flash wrote, but the board still behaves oddly

Read what is actually on it and compare with the shipped image:

& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32c3 --port COM31 read-flash 0x10000 0x80000 "$env:TEMP\node_app.bin"

Roll back to what was there before

This is what §3's backup was for — write the whole saved flash back at 0x0:

& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32c3 --port COM31 write-flash 0x0 "C:\backups\node1_2026-11-25.bin"
& "$env:USERPROFILE\.platformio\packages\tool-esptool\esptool.exe" --chip esp32s3 --port COM32 write-flash 0x0 "C:\backups\hub_2026-11-25.bin"

The hub shows a cot as offline after a flash

The hub's log names where a burst went:

link: node 1: its radio handed over 288 frames since the burst began, 288 of them left it, 0 were refused

handed over == left it with fragments missing means the frames were lost in the air — range or interference, not firmware. refused non-zero means the radio queue is too small, which the shipped build sizes correctly — so if you see it, you are not running the shipped image.

The panel is dark

The hub says “the display could not be started” when the TFT is absent, and that is fine — the monitoring continues. A present TFT that stays dark is wiring: CS 10, MOSI 11, SCK 12, DC 13, RST 14, backlight 4, 3V3, GND. Never wire GPIO35–37 — they are the PSRAM bus.

python firmware/tools/flash_unit.py --check                                    # once, before anything
